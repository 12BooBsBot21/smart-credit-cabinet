# API-контракт — Умный кредитный кабинет предпринимателя

> **Статус документа:** черновик для согласования frontend/backend.  
> **Версия:** 0.1  
> **Backend:** Python + FastAPI (предполагаемый стек)  
> **Формат обмена:** REST API + JSON
>
> Эндпоинты и поля ниже — предложения для MVP, а не окончательно согласованный контракт. Перед реализацией backend-команда должна подтвердить названия, валидацию, авторизацию и форматы ответов.

## 1. Общие правила

- Базовый префикс API: `/api`.
- Тела запросов и ответов — JSON.
- Идентификаторы в примерах — строки; окончательный тип согласовать с backend.
- Даты и время — ISO 8601 в UTC, например `2026-10-23T10:00:00Z`.
- Денежные значения передаются числом в рублях; валюта MVP — RUB.
- Клиентский интерфейс и интерфейс банка используют одно API, но разные права доступа.
- Все данные для демо должны быть синтетическими.
- Фронтенд не должен самостоятельно назначать итоговое решение или менять защищённые статусы заявки.

## 2. Роли

Предварительные роли для демо:

- `client` — создаёт и просматривает собственные заявки.
- `bank_employee` — просматривает заявки и выполняет действия по их обработке.

Способ входа и получения текущего пользователя пока не определён. До реализации согласовать с backend, как будет устроена авторизация. Проверки прав должны выполняться на сервере, а не только скрытием элементов интерфейса.

## 3. Основные сущности

### 3.1. Кредитный продукт

```json
{
  "id": "working-capital",
  "name": "Кредит на пополнение оборотных средств",
  "description": "Синтетический пример кредитного продукта",
  "minAmount": 100000,
  "maxAmount": 5000000,
  "minTermMonths": 3,
  "maxTermMonths": 36,
  "currency": "RUB"
}
```

### 3.2. Заявка

```json
{
  "id": "app-001",
  "productId": "working-capital",
  "status": "draft",
  "amount": 1500000,
  "termMonths": 12,
  "business": {
    "name": "ООО Ромашка",
    "inn": "0000000000",
    "revenueMonthly": 800000
  },
  "createdAt": "2026-10-23T10:00:00Z",
  "updatedAt": "2026-10-23T10:00:00Z"
}
```

> Значения в примерах вымышлены и предназначены только для разработки интерфейса. Не используйте реальные данные клиентов.

### 3.3. Статусы заявки

Предварительный набор статусов:

| Статус                | Значение для UI                   |
| --------------------- | --------------------------------- |
| `draft`               | Черновик                          |
| `submitted`           | Отправлена                        |
| `checking`            | Проверка данных                   |
| `scoring`             | Скоринг                           |
| `needs_information`   | Нужны дополнительные сведения     |
| `approved`            | Одобрена                          |
| `rejected`            | Отказ                             |
| `alternative_offered` | Предложены альтернативные условия |

Backend должен определить допустимые переходы между статусами. Не каждый переход должен быть доступен клиенту.

## 4. Клиентский API

### `GET /api/loan-products`

Получить список доступных кредитных продуктов.

**Ответ `200 OK`:**

```json
[
  {
    "id": "working-capital",
    "name": "Кредит на пополнение оборотных средств",
    "description": "Синтетический пример кредитного продукта",
    "minAmount": 100000,
    "maxAmount": 5000000,
    "minTermMonths": 3,
    "maxTermMonths": 36,
    "currency": "RUB"
  }
]
```

### `GET /api/loan-products/{productId}`

Получить подробности одного кредитного продукта.

**Ответ `200 OK`:** объект кредитного продукта.

### `POST /api/applications`

Создать черновик заявки.

**Запрос:**

```json
{
  "productId": "working-capital",
  "amount": 1500000,
  "termMonths": 12,
  "business": {
    "name": "ООО Ромашка",
    "inn": "0000000000",
    "revenueMonthly": 800000
  }
}
```

**Ответ `201 Created`:**

```json
{
  "id": "app-001",
  "productId": "working-capital",
  "status": "draft",
  "amount": 1500000,
  "termMonths": 12,
  "business": {
    "name": "ООО Ромашка",
    "inn": "0000000000",
    "revenueMonthly": 800000
  },
  "createdAt": "2026-10-23T10:00:00Z",
  "updatedAt": "2026-10-23T10:00:00Z"
}
```

### `GET /api/applications`

Получить заявки текущего клиента.

**Ответ `200 OK`:**

```json
{
  "items": [
    {
      "id": "app-001",
      "productId": "working-capital",
      "status": "submitted",
      "amount": 1500000,
      "termMonths": 12,
      "createdAt": "2026-10-23T10:00:00Z",
      "updatedAt": "2026-10-23T10:05:00Z"
    }
  ],
  "total": 1
}
```

Формат пагинации (`page`, `limit`, курсор или отсутствие пагинации) нужно согласовать. Пример выше — минимальный вариант без параметров пагинации.

### `GET /api/applications/{applicationId}`

Получить подробности заявки, доступной текущему клиенту.

**Ответ `200 OK`:** объект заявки.

### `PATCH /api/applications/{applicationId}`

Изменить заявку, пока она находится в статусе `draft` (и, если это согласуют, `needs_information`).

**Запрос — пример частичного обновления:**

```json
{
  "amount": 1800000,
  "termMonths": 18
}
```

**Ответ `200 OK`:** обновлённый объект заявки.

### `POST /api/applications/{applicationId}/submit`

Отправить черновик на рассмотрение.

**Запрос:** тело отсутствует.

**Ответ `200 OK` (предлагаемый формат):**

```json
{
  "id": "app-001",
  "status": "submitted",
  "submittedAt": "2026-10-23T10:05:00Z"
}
```

После отправки backend запускает обработку или переводит заявку в очередь обработки. Точный механизм определить при реализации.

### `GET /api/applications/{applicationId}/history`

Получить историю изменения статусов.

**Ответ `200 OK`:**

```json
{
  "items": [
    {
      "status": "draft",
      "changedAt": "2026-10-23T10:00:00Z",
      "comment": null
    },
    {
      "status": "submitted",
      "changedAt": "2026-10-23T10:05:00Z",
      "comment": null
    }
  ]
}
```

### `GET /api/applications/{applicationId}/decision`

Получить решение, если оно уже сформировано.

**Ответ `200 OK` — пример одобрения:**

```json
{
  "applicationId": "app-001",
  "status": "approved",
  "approvedAmount": 1200000,
  "termMonths": 12,
  "interestRate": 18.5,
  "reason": null
}
```

Если решение ещё не готово, согласовать один из вариантов: `202 Accepted`, `404 Not Found` или `200 OK` с `decision: null`. Для простоты UI рекомендуется единообразный вариант, который подтвердит backend.

## 5. API рабочего места банка

Эти маршруты доступны только роли `bank_employee`.

### `GET /api/bank/applications`

Получить список заявок на рассмотрении.

Предлагаемые параметры запроса:

- `status` — фильтр по статусу;
- `search` — поиск по идентификатору или названию компании;
- `page` и `limit` — если нужна пагинация.

**Ответ `200 OK`:**

```json
{
  "items": [
    {
      "id": "app-001",
      "businessName": "ООО Ромашка",
      "productId": "working-capital",
      "status": "submitted",
      "amount": 1500000,
      "createdAt": "2026-10-23T10:00:00Z"
    }
  ],
  "total": 1
}
```

### `GET /api/bank/applications/{applicationId}`

Получить расширенные данные заявки для рассмотрения.

**Ответ `200 OK`:** объект заявки и доступные результаты проверок.

### `POST /api/bank/applications/{applicationId}/check`

Запустить проверки полноты и корректности данных, а также имитацию внешних/внутренних проверок.

**Ответ `200 OK` — пример:**

```json
{
  "applicationId": "app-001",
  "status": "checking",
  "checks": [
    {
      "name": "application_completeness",
      "status": "passed",
      "message": "Все обязательные поля заполнены"
    }
  ]
}
```

### `POST /api/bank/applications/{applicationId}/score`

Запустить скоринг или расчёт по правилам.

**Ответ `200 OK` — пример:**

```json
{
  "applicationId": "app-001",
  "score": 72,
  "recommendation": "review",
  "factors": [
    {
      "code": "revenue_stability",
      "label": "Стабильность выручки",
      "result": "medium"
    }
  ]
}
```

Шкала `score`, значения `recommendation` и формат факторов — предложения для демо; согласовать с ответственным за скоринг. Не представляйте синтетический скоринг как реальную банковскую оценку.

### `POST /api/bank/applications/{applicationId}/decision`

Зафиксировать решение по заявке.

**Запрос — пример одобрения:**

```json
{
  "status": "approved",
  "approvedAmount": 1200000,
  "termMonths": 12,
  "interestRate": 18.5,
  "reason": null
}
```

**Запрос — пример отказа:**

```json
{
  "status": "rejected",
  "approvedAmount": null,
  "termMonths": null,
  "interestRate": null,
  "reason": "Не выполнены условия демонстрационной модели"
}
```

Backend обязан проверять допустимость решения и перехода статуса. В реальном продукте такие решения требуют отдельной предметной и юридической проработки; примеры здесь только для прототипа.

### `POST /api/bank/applications/{applicationId}/request-info`

Запросить дополнительные сведения у клиента.

**Запрос:**

```json
{
  "message": "Пожалуйста, укажите дополнительную информацию о выручке.",
  "requiredFields": ["business.revenueMonthly"]
}
```

**Ответ `200 OK` (предлагаемый формат):**

```json
{
  "applicationId": "app-001",
  "status": "needs_information",
  "message": "Пожалуйста, укажите дополнительную информацию о выручке.",
  "requiredFields": ["business.revenueMonthly"]
}
```

## 6. Общий формат ошибок

Предлагаемый единый формат ошибки:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте корректность заполнения полей",
    "details": [
      {
        "field": "amount",
        "message": "Сумма должна быть в допустимом диапазоне"
      }
    ]
  }
}
```

Рекомендуемые HTTP-статусы:

- `400 Bad Request` — запрос невозможно обработать;
- `401 Unauthorized` — пользователь не аутентифицирован;
- `403 Forbidden` — недостаточно прав;
- `404 Not Found` — объект не найден или недоступен;
- `409 Conflict` — действие недопустимо при текущем статусе;
- `422 Unprocessable Entity` — ошибка валидации (часто используется FastAPI);
- `500 Internal Server Error` — непредвиденная серверная ошибка.

FastAPI по умолчанию может возвращать ошибки валидации в своём формате `detail`. Если фронтенду нужен единый формат из примера, это необходимо отдельно реализовать и согласовать.

## 7. Что необходимо подтвердить до реализации

На ближайшей синхронизации frontend/backend подтвердить:

1. Нужна ли авторизация и как для демо переключаются роли `client` и `bank_employee`.
2. Точные поля заявки, обязательность полей и правила валидации.
3. Финальный список статусов и допустимые переходы.
4. Формат решения для одобрения, отказа и альтернативного предложения.
5. Будет ли запрос решения возвращать `202`, `404` или `200` с пустым значением до готовности решения.
6. Нужна ли пагинация и какие параметры фильтрации списка поддержать.
7. Кто и каким запросом запускает проверки и скоринг.
8. Как фронтенд обращается к API в dev-режиме и в Docker.
9. Как будет описан API в OpenAPI/Swagger и как раздавать синтетические данные для демо.

## 8. Предлагаемый порядок реализации

1. Сначала реализовать `GET /api/loan-products`, `POST /api/applications`, `GET /api/applications` и `GET /api/applications/{id}`.
2. Затем добавить отправку заявки и отображение статусов.
3. После этого — банковский список заявок, проверки, скоринг и решение.
4. До готовности backend использовать моковые реализации с теми же типами данных и контрактами.

**Примечание:** это стартовый проектный контракт. Он не заменяет согласование с backend-разработчиком и должен обновляться по мере принятия решений командой.
